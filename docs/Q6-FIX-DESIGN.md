## 1. 증상 — 질문 1회가 거짓 답변을 냈다

**질문**: *"리디안솔루션은 무엇을 하는 회사야?"* (2026-08-23, `searchId s-20260823-015603-m1n9`)

| 답변의 주장 | 실제 | |
|---|---|---|
| 설립 연도 **없음** | `리디안솔루션(주) 설립` Event **있음** | ❌ 거짓 |
| 주요 고객사 명단 **없음** | `R-TAPs 납품: H 중공업, H 제철, D 전자` 등 **4건 있음** | ❌ 거짓 |
| 매출 없음 | 없음 | ✅ |
| 임직원 수 없음 | 없음 | ✅ |

**검색도 챗도 정상이었다.** 시드를 정확히 잡았고(`리디안솔루션` T1), 1홉을 정직하게 확장했고, 못 찾은 것을 못 찾았다고 보고했다. **거짓말을 한 것은 데이터다** — 회사가 두 노드로 갈라져 한쪽만 밟혔다.

```
리디안솔루션      관계 28  ← p02·p03·p05   (검색이 밟은 쪽)
리디안솔루션(주)   관계 34  ← p01·p04·p07   (통째로 누락)
두 조각 사이 최단 경로 = 2홉 (리디안솔루션 → SAP → 리디안솔루션(주))
```

## 2. 원인 — 스키마가 **다른 도메인(만화)용 시드 그대로**다

`[실측]` 시드 라벨 16종 중 readians 코퍼스가 쓴 것은 **8종뿐**이고, 나머지 8종은 전부 만화 전용이다.

| 미사용 (만화 전용) | Family · TimePeriod · Species · Weapon · Mission · Training · MediaRange · StorySegment |
|---|---|
| **사용** | Person 3 · Organization 34 · Place 7 · Event 20 · **Object 22** · Technique 2 · **Concept 78** · Work 4 |

**`Concept`에 78개(전체 152의 절반 이상)가 몰렸다** — 쓰레기통 라벨이 됐다.

**SAP 제품이 갈 곳이 없다.** 후보 둘의 설명이 이렇다:

- `Object` = *물건·도구·물질*
- `Concept` = *추상 개념·이론·용어·제도·프로세스*

**소프트웨어 제품은 둘 다 그럴듯하고 둘 다 맞지 않는다.** 그래서 모델이 파일마다 다르게 골랐다 — 이것이 라벨 분리 9건의 전부다.

**결정적 증거**: `schema_version`이 **1 그대로**다. 6개 파일을 생성하는 동안 **신규 유형이 0건 도출**됐다. SAP 컨설팅 회사 웹사이트를 6장 읽고 새 유형이 하나도 필요 없었다는 것은 정상이 아니다 — 프롬프트의 *"기존 유형 **우선 재사용**"* 지시가 만화용 라벨에 억지로 우겨넣게 만들었다.

> 이전 기록(2026-08-22 DECISIONS)에서 `schema_version` 미상승을 *"기존 유형 우선 재사용이 작동한 정상"* 이라고 적었다. **그 해석을 정정한다** — 작동한 것이 아니라 **과작동**했다.

## 3. 정본이 이미 경고한 것 (반박 렌즈)

`TECH-SPEC §2.1.5`:

> *"LLM 비결정성에 의한 파일 간 명칭 비일관은 **지시문만으로 완전히 강제할 수 없으므로**, 하류 방어로 재빌드 시 유사 이름 쌍 리포트를 두고, **반복 검출 시 별칭 사전(후순위)을 앞당기는 트리거**로 삼는다."*
> *"선택 옵션(후순위 검토): 생성 프롬프트에 **기존 그래프의 동일 라벨 노드명 상위 N개를 주입**해 명칭 수렴을 유도(토큰 비용과 교환)."*

**그리고 `instructions_ko`에는 이미 이 규칙이 있었다**:

> *"고유명사는 자료에 등장하는 가장 완전한 정식 명칭으로 통일한다(별명·약칭 금지). **같은 대상은 반드시 같은 name으로 쓴다.**"*

**규칙이 있는데 실패했다.** ⇒ **명칭 문제를 "지시문 강화 + 재생성"으로 푸는 것은 이미 실패가 증명된 경로다.** 라벨 문제는 다르다 — 규칙이 **아예 없었으므로** 라벨 신설은 유효할 여지가 크다.

## 4. 수리안 — 두 문제를 다르게 푼다

### 4-A. 라벨 (분리 9건) — **스키마 정비**로 푼다

신규 라벨 **1종**을 등재하고 경계 규칙을 `instructions_ko`에 넣는다.

```
Product(제품/솔루션): 상용 소프트웨어 제품·솔루션·플랫폼·모듈
  예) SAP GRC, SAP BTP, SAP S/4 HANA, GRC K-PACK, FTA R-TAPs, ReadiFlow
```

경계 규칙(추가할 지시문):
- *"판매·배포되는 소프트웨어 제품·솔루션·플랫폼은 `Product`로 한다. `Object`(물건)나 `Concept`(개념)로 쓰지 않는다."*
- *"`Concept`는 제품·조직·장소·사건 어디에도 속하지 않는 추상 개념에만 쓴다."*

**미사용 만화 라벨 8종은 지우지 않는다** — 예시 그래프(귀멸의 칼날) 복원에 필요하고, 지우는 것은 되돌리기 어려운 변경이다.

### 4-B. 명칭 (분리 1건 + 파생) — **선택 필요**

| 안 | 방법 | 엔진 호출 | 되돌리기 | 정본 위상 |
|---|---|---|---|---|
| **B1. 별칭 사전** | 주입 단계에서 `리디안솔루션` → `리디안솔루션(주)` 정규화. 원본 JSON 불변 | **0회** | 사전 1줄 삭제 | `§2.3.2` *"별칭 사전은 후순위"* → **앞당김. TECH-SPEC 개정 필요** |
| **B2. 재생성** | 정본 명칭을 지시문에 박고 6건 반려·재생성 | **6회** | 반려 이력 보존 | 현행 정본 그대로 |
| **B3. 기존 노드명 주입** | 생성 프롬프트에 현 그래프의 동일 라벨 노드명 상위 N개 주입 | 6회 + 코드 변경 | 코드 되돌림 | `§2.1.5`가 명시한 *"선택 옵션"* |

**정본 명칭 후보**: `리디안솔루션(주)` — 근거는 `instructions_ko`의 *"가장 완전한 정식 명칭"* 규칙과 p01 푸터의 법인 표기(`alias_full: READIAN SOLUTION`).

## 6. 실행 순서 (승인 후)

1. `shared/schema/schema.default.json` + `data/schema.json`에 `Product` 등재 + 경계 규칙 3줄 추가 (`schema_version` 1→2)
2. 4-B에서 택한 안 실행
3. 재빌드 → 같은 질문 재측정 → 위 6항 대조표
4. `DECISIONS.md` 기록 · `MAINTENANCE-PLAN.md` Q6 마감

**되돌리기**: 스키마는 git 추적(시드)이라 커밋 되돌림. 재생성분은 `Rejected/`에 이력 보존. DB는 `kg_rebuild` 1회로 언제든 재조립.

## 7. 이 설계안이 다루지 않는 것

- **Q5**(나열→소속 추론)·**Q7**(시점 소실)은 별건이다. 같이 고치면 어느 조치가 무엇을 고쳤는지 분간할 수 없다(M2에서 한글화를 뒤로 미룬 것과 같은 논리).
- 미사용 만화 라벨 8종 정리 — 예시 데이터 의존성이 있어 별건.
