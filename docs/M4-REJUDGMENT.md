## 1. 판정 세션 운영 — **새 채팅이냐 `/clear`냐**

**결론: 둘 중 아무거나 써도 된다.** 목적은 하나 — **직전 대화의 검색 결과를 모델의 눈앞에서 치우는 것**이다. 새 채팅은 확실하고, `/clear`도 같은 목적을 달성한다(2026-08-21 판정에서 E1·E2·E3를 `/clear`로 실행하고 "청정"으로 기록한 실적이 있다 — `[문서] spike-judgment-log.md:30~32`).

### 어느 문항에 필요한가 — **전부는 아니다**

| 문항군 | 세션 처리 | 왜 |
|---|---|---|
| **D1·D2·D3 · E1·E2·E3** (6문) | **문항마다 새 채팅 또는 `/clear`** | 이 6문이 재는 것은 **①호출 여부**다. 앞 문항의 검색 결과가 대화에 남아 있으면 모델이 "이미 아는데 굳이?" 하고 도구를 건너뛴다 — 지표가 무효가 된다 |
| **A3·B1·B2·B4·C4** (5문) | **연속 대화 그대로 진행** | 이 5문이 재는 것은 **②시드·③인용·④3상태**이고, 셋 다 **도구가 돌려준 값**이라 대화 맥락에 오염되지 않는다 |

### ⚠️ 대신 생기는 부작용 — **⑤ 소요 시간이 부풀어 오른다**

개선 전 실측에서 **새 컨텍스트 첫 질문은 12~16초**, 연속 대화 안에서는 **5~7초**였다(컨텍스트·규칙을 새로 읽는 시간).

> **정정(2026-08-22)**: `spike-judgment-log.md:67`은 *"예산 10초를 넘긴 4건은 전부 새 컨텍스트 첫 질문"* 이라 적었으나 **4건 중 3건**이 맞다 — 초과 4건은 C1 11.9초 · E1 15.6초 · E3 12.3초(새 컨텍스트) + **D1 11.6초(연속 대화 재실행)** 이고, D1이 연속이라는 것은 같은 문서의 D1 행 비고(*"오염 주석: 같은 질문 재실행(연속 대화)"*)가 스스로 밝히고 있다. 계측 도구를 모집단별로 고치면서 드러난 자기모순이다.

⇒ **⑤는 두 모집단을 섞지 말고 나눠 적는다.**

| 모집단 | 개선 전 기준선 `[실측]` | M4 판정 |
|---|---|---|
| 새 컨텍스트 첫 질문 | 6건 · **중앙값 11.9초** · 최대 15.6초 | **합격 판정에 쓰지 않는다**(참고 표시만) |
| 연속 대화 | 21건 · **중앙값 5.6초** · 최대 11.6초 | **중앙값 ≤10초** |

> **모집단은 문항군이 아니라 대화 위치로 갈린다.** 개선 전 기준선의 새 컨텍스트 6건은 실제로 **C1·E1·E3·D2·E2·A2**였다 — D·E군과 일치하지 않는다. 문항 번호로 짐작하지 말고 **도구가 출력한 모집단 열**을 그대로 쓸 것.

섞어서 중앙값을 내면 **개선과 무관한 이유로 미달이 뜬다.** 이것이 이번 실행표에서 가장 틀리기 쉬운 지점이었다.

> **v2에서 도구를 고쳤다.** v1 시점의 `measure-latency.mjs`는 ①모집단 구분이 없고 ②합격 판정을 **최대값** 기준으로 찍어 D·E군 때문에 항상 `초과 있음 ✗`가 나왔으며 ③과거 회차와 섞였다. 지금은 모집단을 자동 분류(세션 파일의 첫 측정 질문 = 새 컨텍스트)하고, **연속 대화 중앙값**으로만 합격을 판정하며, `--since`로 회차를 분리한다. 자동 분류가 틀리면 `--fresh A3,D1` / `--continuous B1`로 덮어쓴다.

### 진행 순서 권고

**A3 → B1 → B2 → B4 → C4** (연속 대화 5문, 문항마다 ④ 대조) → **`/clear`** → **D1** → `/clear` → **D2** → `/clear` → **D3** → `/clear` → **E1** → `/clear` → **E2** → `/clear` → **E3**

> ⚠️ **`/clear`를 쓰기로 했다면 소요 집계에 `--fresh D1,D2,D3,E1,E2,E3`를 반드시 붙인다.** 자동 분류는 **세션 파일**의 첫 질문만 새 컨텍스트로 보는데, `/clear`가 같은 파일 안에서 일어나면 그 6문이 전부 연속으로 분류돼 **v2가 제거하려던 오염이 그대로 재현된다**(개선 전 데이터에서 실제로 D1·D3·E2가 그렇게 섞여 있었다). 새 채팅을 쓰면 자동 분류로 충분하다.

### ⚠️ A3에서 **복원 문구가 안 뜨는 것이 정상이다**

키워드 손상은 **모델이 매번 일으키는 것이 아니다**(실측 손상률 5.4%). A3에서 모델이 `일륜도`를 정상으로 넘기면 그냥 **T1 적중**이고 재검색 문구는 뜨지 않는다 — **이것이 통과다.** 반대로 손상이 재발하면 아래 문구가 뜨고, 그때도 **시드 1건(일륜도:T1)으로 적중**해야 한다.

```
키워드 자동 재검색 1건: '일륨도'는 그래프에 없어, 이 호출의 question에서
자모 1개만 다른 '일륜도'로 다시 검색함 (자동 추정 — 확정된 오타 판정이 아니다)
```

손상이 실제로 재발하면 **그 자체가 귀중한 관측 표본**이므로 비고에 반드시 남긴다(현재 표본 n=2).

### 회귀로 오인하지 말 것 — 개선 후 **새로 나타나는 문구 2종**

| 문구 | 언제 | 성격 |
|---|---|---|
| `키워드 자동 재검색 N건: …` | 손상 키워드가 복원됐을 때 | **설계된 출력** |
| `1층의 n건 중 m건을 인용했습니다 — 2층이 1층과 거의 같아 강조 대비가 낮습니다.` | 인용이 1층의 50%를 넘을 때 | **설계된 출력**(옛 `과잉 인용 의심`의 서술형 교체본). A3처럼 1층이 작은 문항에서 정상적으로 뜬다 |

반대로 **사라져야 할 문구**: `과잉 인용 의심` · `0.5 스파이크 준비`. 둘 중 하나라도 보이면 구버전이 돌고 있는 것이다.

## 4. 판정 ④ 자동 대조 — 육안 대신 이 절차

**문항 11개 각각**에 대해, 문항 직후(다음 문항 넘어가기 **전**) 실행한다 — 합격선 7번의 임계값이 11/11이다. `data/runtime/last-searches.json`이 **5건 롤링**이라 미루면 밀려난다. *(v1 시점에는 이 절차가 0회 실행된 채 "도구 자체 검증 11/11"이 문항 판정으로 오인될 뻔했다.)*

3. 출력의 마지막 줄 `판정 ④: k/11 통과`를 기록 양식에 옮긴다.

**무엇을 검사하나**: searchId·질문 원문 일치 / 1층 노드·관계 kgid 집합이 푸시한 것과 동일 / N 일치 / 2층 ⊆ 1층 / 렌더 1층·2층 겹침 없음(2층 우선 규칙) / M == 실제 렌더 총수 / citation 상태와 2층 존재의 정합.

**`ℹ N/M 격차` 안내는 실패가 아니다** — 현재 화면에 없는 kgid(필터로 숨겨졌거나 그래프가 낡음)의 내역이며, 그것이 곧 화면의 `N개 중 M개 표시 중` 문구의 근거다.

**이 도구가 증명하지 않는 것**: 앱이 **어느 집합을 어느 상태로 판정했는가**까지다. 그 판정이 **실제로 그 색으로 칠해졌는지**는 증명하지 않는다(스냅샷과 색 적용은 평행 경로 — TECH-SPEC §7.9).

### 4-b. 색 적용까지 확인하기 (대표 문항 2~3개)

3D 뷰가 **실제 크기로 렌더 중일 때** 브라우저 콘솔에서 아래를 실행해 세 상태의 **개수**를 센다.

```js
(() => { const n=[],l=[]; window.scene.traverse(o=>{const d=o.__data; if(!d) return;
  const m=Array.isArray(o.material)?o.material[0]:o.material; if(!m?.color) return;
  const c='#'+m.color.getHexString(); (d.source!==undefined?l:n).push(c); });
  const t=a=>a.reduce((m,c)=>(m[c]=(m[c]||0)+1,m),{}); return {노드:t(n), 관계:t(l)}; })()
```

| 상태 | 색 | 기대 개수 |
|---|---|---|
| 2층 | `#facc15` | `layer2` |
| 1층 전용 | 노드=원색 밝기상향 / 관계=`#e2e8f0` | `layer1 − layer2` |
| 밖 | `#475569` | `전체 − layer1` |

**전제**: 뷰포트가 0×0이면 캔버스가 생성되지 않아 `window.scene`이 없다 — 크기를 준 뒤 새로고침할 것. 좌표·크기·파티클은 여전히 육안 몫이다.

### 이 10문이 **증명하지 못하는 것** (2026-08-22 적대적 검증 반영 — v2에서 정직화)

v1은 이 대조를 "무개입 증명"이라 적었다. **과장이었다.** 실측으로 확인된 한계 넷:

| 한계 | 실측 |
|---|---|
| **T2 하한에 대한 판별력 0** | 10문 중 T2 분기 진입은 4건뿐이고, 그 4건에서 하한(0.5)에 걸리는 후보는 **0건**(최저 비율 기유 0.62). 하한이 실제로 무는 3건(S07·M03·M05)은 10문에서 전부 빠졌다 |
| **앵커 복원에 대한 판별력 0** | 복원은 `records.length === 0`에서만 호출되는데 10문은 전부 시드 적중 → **도달 0건** |
| **M3 문구에 대한 커버리지 0** | `capture-golden.js`는 `runSearch`를 직접 부르고 `kgCite.js`·`kgStatus.js`를 **한 번도 지나지 않는다** |
| **재실행은 새 증거가 아니다** | 코드·데이터가 그대로면 동일 출력은 결정론의 산술적 필연이다. 실제로 M2 직후 캡처와 M4 캡처가 **MD5까지 동일**했다 |

**따라서 2단의 정확한 역할은 "증명"이 아니라 회귀 감시**다 — *"선언한 3건(S07·M03·M05) 외에 다른 것이 바뀌지 않았다"* 를 확인하는 것이며, 그 이상을 주장하지 않는다. 개선의 실효는 **3단과 챗 5문**이 증명한다.

**산출물 자기식별(v2 신설)**: 캡처 파일에는 이제 `capturedAt`(실제 시각)과 `gitHead`(캡처 시점 커밋)가 기록된다. 대조 보고에 이 두 값을 인용해 **어느 코드로 뜬 픽스처인지**를 증명할 것. *(이 필드 도입 **이전**에 뜬 두 파일 `golden-searches.json`·`golden-searches-postM2.json`은 값이 없고, 게다가 `capturedStamp`·`purpose`가 서로 글자까지 같아 **산출물만으로는 구별되지 않는다**. 두 파일의 출처는 각각 커밋 `3358353`·`532b151`이 근거이며, 이후 회차부터 이 문제가 사라진다.)*
